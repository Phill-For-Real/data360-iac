# Example manifests

Ready-to-use manifests for testing `sf data360` commands end to end against the real Salesforce
Data 360 Connect REST API. None of these require a real org to `validate` or `graph`;
`plan`/`apply`/`destroy` need an authenticated org.

| File                                                                         | What it demonstrates                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [asset-maintenance.json](asset-maintenance.json)                             | The full worked example as a single file: 26 declared resources plus 5 `kind: "data"` lookups of real Salesforce standard DMOs, across fourteen core resource types — three real `IngestApi` connections/streams (Account, Vehicle, Vehicle Telematics Event) feeding the real `ssot__Account__dlm`/`ssot__ContactPointAddress__dlm`/`ssot__ContactPointPhone__dlm`/`ssot__Vehicle__dlm`/`ssot__VehicleTelematicsEvent__dlm` standard DMOs via 5 field mappings, a data transform (STL node-graph, into its own owned output DLO), identity resolution (producing the real `UnifiedAccount__dlm` DMO), a calculated insight, two segments and two activations built on that Unified Account DMO (with a Data Cloud activation target — no external credentials needed), plus a data governance flow across four of the five governance types: an `AccessPolicy` with a record-level `AccessPolicyRule`, two `TagAssignment`s (PII/sensitivity tagging on DLO fields, referencing the real built-in `PersonalData.*` tag taxonomy), and a `ClassificationAssignment`. No `ObjectAccessGrant` -- unlike tags/classifications, a permission set has no built-in equivalent to reference, so add one yourself if you need this governance type. Confirmed end-to-end against a live org. Use this for the main `validate` → `plan` → `apply` → `destroy` walkthrough. |
| [asset-maintenance-directory/](asset-maintenance-directory/)                 | The exact same 31 blocks, split across five files (`connections.json`, `schema.json`, `identity-resolution.json`, `segments-and-activation.json`, `governance.json`) to demonstrate directory-manifest loading — point `-f` at the directory instead of a file.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| [minimal-connection.json](minimal-connection.json)                           | A single `Connection` resource — the fastest way to sanity-check `validate`/`plan`/`apply` against one resource before working with the full manifest.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| [customer-service-data-reference.json](customer-service-data-reference.json) | A second, smaller manifest that looks up a `DataModelObject` as a `kind: "data"` block instead of creating one, then tags one of its fields as PII and classifies that tag (referencing the same real built-in `PersonalData.Location.StreetAddress`/`DataCategorization.DataCompliance.PII` taxonomy entries) — demonstrates governance declared against a referenced (not just owned) object. **Note:** this file's lookup name (`Account_DMO__dlm`) and field name (`BillingAddress`) predate `asset-maintenance.json`'s real-schema rewrite and are placeholders, not real standard-DMO names — swap in a real one (e.g. `ssot__Account__dlm`, matching `asset-maintenance.json`'s own lookups) before running `plan`/`apply` against a live org.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Try it

```bash
# Static checks only -- no auth needed.
sf data360 validate -f examples/minimal-connection.json
sf data360 validate -f examples/asset-maintenance.json
sf data360 validate -f examples/asset-maintenance-directory
sf data360 validate -f examples/customer-service-data-reference.json

# Visualize the dependency graph.
sf data360 graph -f examples/asset-maintenance.json --format dot
```

See [../GUIDE.md](../GUIDE.md) for the full `init` → `plan` → `apply` → `destroy` workflow using
these files.
